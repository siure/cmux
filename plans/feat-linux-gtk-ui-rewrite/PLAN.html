Implementation plan · Linux / GTK4

Rewrite the shell, keep the product.

A complete GTK presentation rewrite that brings the Linux port to the density, clarity, stability, and terminal-first feel of normal cmux—without rewriting the Rust core, Ghostty integration, WebKit runtime, session model, or socket API.

01 · Executive summary

The rewrite boundary is the GTK presentation layer.

The Linux port already implements most of the product. The problem is not missing capability; it is that nearly every UI concern lives inside one large file, consumes untyped JSON snapshots, refreshes through polling, and carries hardcoded styling. That structure makes the interface visually inconsistent, fragile while editing, and expensive to improve.

Keep

AppState, socket commands, session persistence, Ghostty, WebKitGTK, browser profiles, Canvas state, custom sidebar documents, and CLI behavior.

Replace

The GTK shell, widget ownership, snapshot parsing, CSS organization, focus routing, component reconciliation, and coarse polling loop.

Deliver

A compact native Linux UI that visually reads as cmux, retains surface identity, updates reactively, and can be tested one component at a time.

Core rule: do not mechanically split gtk_ui.rs into smaller files and call that a rewrite. The rewrite is complete only when untyped parsing, periodic full refresh, broad reconstruction, and cross-component ownership are removed.

03 · What is wrong today

The current UI is both visually inefficient and difficult to refine safely.

The screenshot below was captured from the current GTK build on 2026-07-25 at 1504×1436. It confirms that the usability problem is not abstract: chrome, cards, duplicated labels, and wide side regions consume a large share of the window while the terminal content remains sparse.

Toolbar dominates the workspace

A full row of large bordered buttons exposes installation, split, terminal, palette, and help actions at all times. Normal cmux keeps these actions compact, contextual, or in menus.

Pane chrome is nested like cards

Each split has an outer border, internal padding, a tab card, a duplicated surface:n · terminal label, and another inset terminal rectangle. The canonical UI uses one thin tab strip and lets content meet pane edges.

Useful width is squeezed

The workspace sidebar, broad pane gutters, and always-visible right sidebar leave narrow terminals even in a 1504 px window. The reference UI fits more panes while preserving readable columns.

Hierarchy exposes implementation details

The title shows workspace:2 · pane:2 · surface:2; pane labels repeat internal IDs; generic action names compete with the actual task. User-facing titles, status, branch, and notification context should lead.

Sidebar density is poorly balanced

Rows truncate early despite ample vertical space, selection resembles a large card, and the close control floats outside the row. Normal cmux fits richer metadata with tighter alignment and less framing.

Terminal presentation is not trustworthy

The captured fallback terminal text wraps and overlaps awkwardly. The rewrite must treat embedded Ghostty as the primary production path and isolate fallback previews from the main UI contract.

04 · UX invariants

These rules are not negotiable.

  1. Stable surfaces: ordinary workspace, tab, split, sidebar, and layout changes must not recreate Ghostty or WebKit hosts.
  2. Typing first: a terminal key event must not build snapshots, traverse unrelated widgets, or wait for the app-wide model lock.
  3. One focus owner: terminal, browser content, omnibar, sidebar, settings, palette, document, and dialog focus are explicit states.
  4. Draft safety: rename, search, omnibar, settings, TextBox, and agent prompt drafts survive unrelated updates and failed submissions.
  5. Shared actions: keyboard, click, menu, palette, CLI, socket, Ghostty, and WebKit callbacks converge on the same core mutation path.
  6. Topology integrity: pane tabs are independent from split geometry; Canvas and Splits reuse the same surface hosts.
  7. Attention consistency: sidebar badges, tab dots, pane rings, desktop notifications, and jump-to-unread derive from one notification index.
  8. Native input: IME, compose sequences, clipboard and primary selection, web shortcuts, terminal mouse reporting, and drag-and-drop keep working.
  9. Accessibility: every state conveyed by color is also represented by text, icon, accessible state, or structure.
  10. Incremental parity: no feature disappears while its replacement is under construction.
05 · Target architecture

Three layers with one-way ownership.

Keep the authoritative product model display-independent. Insert a typed UI projection and event bridge. Make GTK responsible only for native widgets, local edit state, focus, and stable surface hosting.

    ├── focus.rs               # explicit FocusContext
    ├── style.rs               # resource installation + metrics
    ├── shell/                 # titlebar, root, overlays, sidebars
    ├── workspace/             # virtualized groups and rows
    ├── panes/                 # tab strips, split tree, Canvas
    ├── surfaces/              # one controller per surface kind
    └── widgets/               # small reusable native controls

Typed projection

  • GTK receives Rust structs and enums, never arbitrary protocol JSON.
  • The existing renderer JSON contract is produced by serializing the typed model.
  • Each independently updated subtree carries a monotonic revision.
  • Compatibility aliases and defaults live in one adapter.

Event-driven updates

  • All authoritative mutations publish a typed UiChange.
  • Changes are coalesced by window and domain before GTK reconciliation.
  • Revision gaps trigger a scoped full snapshot, not a permanent poll.
  • Ghostty rendering stays on Ghostty wakeups; terminal frames never enter the UI event bus.

Stable controllers

  • Controllers are keyed by window, pane, or surface identity.
  • Updates mutate properties and models rather than replacing complete subtrees.
  • A window-scoped registry owns Ghostty, WebKit, and native document hosts.
  • Detach/attach is explicit and testable during topology changes.

Local edit state

  • Clean → Editing → Submitting → Reconciled / Failed.
  • Request IDs pair optimistic state with authoritative results.
  • Failure retains the draft and shows an inline error.
  • Focus restoration uses explicit tokens, not widget-tree searches.
06 · Visual system

Make the product visually coherent before polishing individual widgets.

Palette

Near-black and warm charcoal surfaces; gray hierarchy; one saturated blue accent; terminal colors remain content, not chrome.

Density

28–32 px pane tabs, 30–34 px compact controls, thin dividers, minimal gutters, and no large card padding in the main shell.

Typography

System sans for chrome, monospace for paths/branches/technical metadata, restrained weight differences, and no oversized headings in runtime UI.

Selection

Solid blue compact workspace selection; subtle active-tab underline/background; 2 px pane focus or unread ring without layout shift.

Icons

Symbolic monochrome icons using current color. Avoid emoji and one-off colored image controls.

Modes

Dark, light, high contrast, 200% text scaling, and reduced motion. Chrome may derive safe semantic colors from the active Ghostty theme.

07 · Component plan

Rewrite by stable visual region.

Each component owns its native widgets and local interaction state, receives immutable view models, and emits typed actions.

Window shell and titlebar
  • One WindowController per model window.
  • Compact client-side header with native compositor window controls.
  • Sidebar, notification, new-workspace, right-sidebar, and layout actions stay compact.
  • Workspace title and remote/directory context are single-line and ellipsized.
  • Command palette, shortcut help, drag targets, and banners live in an overlay layer.
Left workspace sidebar
  • GtkListView + typed gio::ListStore; do not rebuild a vertical box.
  • Group headers, pinned partitions, collapse, multi-selection, inline rename, context menus, reorder, and group drops.
  • Rows receive value snapshots plus actions, never the full store.
  • Fixed slots for unread/status controls prevent title and metadata from jumping.
  • Custom sidebars mount through a separate provider controller.
Pane tabs and split tree
  • One stable tab-strip controller per pane.
  • Horizontal scrolling, selected/hover/unread/loading states, close controls, new terminal, split, and overflow actions.
  • Typed recursive PaneNodeVm::Leaf | Split; do not infer topology from floating-point frames.
  • Reuse unchanged GtkPaned nodes and pane hosts.
  • Divider changes remain local during drag and commit at release or a bounded rate.
Terminal surfaces
  • Retain gtk_ghostty.rs as the native rendering/input boundary.
  • Move shell chrome, search, TextBox, focus, and context-menu concerns into the terminal controller.
  • Direct key, IME, pointer, selection, scroll, and clipboard paths to Ghostty.
  • No application draw loop and no snapshot work on keystrokes.
  • Fallback preview renderers remain isolated from the production Ghostty controller.
Browser surfaces
  • Retain gtk_webkit.rs as the dynamic WebKit runtime boundary.
  • Keep views alive across workspace and tab switches; recreate only for profile/data-store generation changes.
  • Compact back/forward/reload, security state, omnibar, loading progress, profile, find, downloads, and overflow controls.
  • Omnibar suggestions update independently; typing never rebuilds the pane.
  • Replace evaluation, screenshot, PDF, and recording polls with controller-bound request channels.
Canvas
  • Keep Canvas as an independent presentation controller using the existing model.
  • Reuse surface hosts while changing only their container and geometry.
  • Preserve pan, zoom, snapping, guides, minimap, culling, z-order, and persisted viewport state.
  • Plain scroll remains local to content; modifier gestures control the Canvas.
Notifications and attention
  • One typed index keyed by workspace and surface.
  • Sidebar badge, tab dot, pane ring, notification center, desktop delivery, and jump ordering share that index.
  • Use a 2 px ring that does not alter pane allocation.
  • Short flash animations respect reduced motion and remain separate from persistent unread state.
Right sidebar, settings, and dialogs
  • Files, Find, Sessions, Feed, and Dock have separate controllers under a shared sidebar shell.
  • Virtualize large lists and move filesystem traversal off the main thread.
  • Settings use a category list with lazily created typed pages and consistent row anatomy.
  • A dialog coordinator serializes close, resume, paste, clipboard, auth, and destructive confirmations per window.
  • All controls expose accessible roles, names, values, states, and keyboard equivalents.
08 · Migration phases

Keep the app usable throughout the rewrite.

PHASE 0

Baseline and fixtures

Capture current behavior, deterministic renderer fixtures, Linux screenshots, focus flows, surface-identity counters, and performance traces. Add the legacy/next selector.

Gate: legacy UI remains the default and all current features are still available.
PHASE 1

Typed UI model

Create ui_model. Build the public renderer JSON by serializing typed snapshots and prove compatibility with representative fixtures.

Gate: no visible UI change; socket and renderer contracts remain compatible.
PHASE 2

Runtime bridge and change hub

Introduce AppHandle, typed actions, revisioned change events, and event completeness instrumentation. Route GTK and socket mutations through the same gateway.

Gate: legacy GTK can render while diagnostics prove all mutation domains invalidate correctly.
PHASE 3

New shell and design resources

Build application/window registry, titlebar, root layout, overlays, focus controller, CSS resources, metrics, and theme modes behind CMUX_LINUX_UI=next.

Gate: launch, restore, multi-window, fullscreen, close, and focus work.
PHASE 4

Workspace sidebar

Ship virtualized rows, groups, selection, badges, metadata, rename, context menus, drag-and-drop, and custom-sidebar provider switching.

Gate: all workspace management entry points pass behavior-level parity tests.
PHASE 5

Pane chrome and topology

Ship stable tab strips, pane hosts, recursive split reconciliation, divider persistence, focus rings, and surface registry integration.

Gate: workspace, tab, and split operations do not recreate Ghostty/WebKit hosts.
PHASE 6

Surface controllers

Migrate terminal, browser, document, Markdown, diff, project, agent session, feedback, and Canvas one surface family at a time.

Gate: each migrated family has focused tests and a temporary component-level fallback.
PHASE 7

Right sidebar, settings, notifications, dialogs

Complete the remaining shell regions, command palette, shortcut help, accessibility, and string catalog.

Gate: all settings, beta gates, custom sidebars, notification flows, and keyboard-only paths are represented.
PHASE 8

Remove polling

Disable the 500 ms snapshot loop and browser request timers. Keep an opt-in low-frequency recovery poll for one release while event completeness soaks.

Gate: no stale-state failures in long-running, multi-window, external-socket, and background-process scenarios.
PHASE 9

Cut over and delete legacy UI

Make the next shell the default, retain one emergency flag window, migrate remaining tests, then remove gtk_ui.rs and temporary compatibility paths.

Gate: two stable release cycles without a rollback-class issue.
09 · Validation

Test appearance, behavior, identity, and accessibility.

Unit

  • Typed projection and serialization compatibility.
  • Change masks and event completeness.
  • Draft, focus, selection, tabs, split tree, and notification reducers.
  • Every UI entry point maps to the shared action path.

Component

  • Apply immutable view models and assert widget properties, ordering, CSS classes, and accessible state.
  • Apply a second model and prove widgets are reused.
  • Verify focused editors are protected and errors retain drafts.

Integration

  • Xvfb for X11 and headless Weston for Wayland.
  • Drive UI state through the public socket.
  • Separate real Ghostty and WebKit smoke lanes.
  • Multi-window, restore, drag/drop, IME, clipboard, and external mutation coverage.

Visual and accessibility

  • Pinned GTK, fonts, icons, scale, locale, renderer, and viewport.
  • Golden scenarios based on the canonical cmux compositions.
  • Semantic geometry assertions alongside image diffs.
  • AT-SPI roles, names, values, focus order, and keyboard actions.

Required visual scenarios

  • Dense nested terminal splits
  • Mixed terminal and browser panes
  • Unread sidebar badge and pane ring
  • Workspace groups and long metadata
  • Right sidebar Files and Find
  • Command palette and shortcut help
  • Settings in dark, light, and high contrast
  • Canvas overview and focused offscreen pane
  • Narrow 900×700 layout
  • Scale factors 1× and 2×
macOS screenshots are composition references, not pixel goldens. The executable goldens must be Linux screenshots produced in a pinned test environment.

11 · Rollout and risks

Use one top-level selector and time-bounded component flags.

  • CMUX_LINUX_UI=legacy|next is the developer and emergency selector.
  • Component flags choose implementations at controller construction; do not scatter leaf-level conditionals.
  • Recommended rollout: developer opt-in → nightly default → stable opt-in → stable default → legacy deletion.
  • Active UI implementation and migration flags must appear in renderer diagnostics and support reports.

13 · Definition of done

The UI must be both better-looking and structurally better.

  • gtk_ui.rs is removed.
  • GTK consumes typed snapshots and emits typed actions.
  • Protocol JSON parsing is confined to compatibility boundaries.
  • The 500 ms snapshot poll and browser request polls are gone.
  • Revision-gap recovery works without permanent background polling.
  • Ghostty and WebKit identity remains stable through normal navigation and layout changes.
  • Sidebar, pane tabs, splits, browser chrome, and notification rings visibly match the cmux north star.
  • Dark, light, high contrast, scaling, and reduced motion are supported.
  • Terminal typing, IME, clipboard, browser focus, drag/drop, shortcuts, and chords pass on X11 and Wayland.
  • Settings, notifications, sidebars, Canvas, documents, diffs, projects, and agent sessions have typed controllers.
  • Visual, semantic, AT-SPI, identity, and performance gates pass.
  • Socket, renderer, persistence, and automation contracts remain compatible.
  • The new shell ships as default for two stable cycles without a rollback-class issue.
  • The legacy kill switch and temporary component flags are deleted.
Final acceptance test: open the canonical dense workspace scenario on Linux. It should immediately read as cmux—compact workspace navigation, stable nested panes, quiet chrome, clear focus and unread state, and nearly all available space devoted to work.
